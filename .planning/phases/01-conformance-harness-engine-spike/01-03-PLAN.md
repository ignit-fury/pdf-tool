<objective>
Build the independent verifier that cross-checks the corpus manifest against the actual files
using only plain structural inspection (D-04), the private-tier fetch mechanism that treats a
missing bucket credential as a normal state rather than a failure (D-01, D-02), the CI wiring that
actually runs the prober and the render/validate harness against the private tier once it is
fetched, and the mechanical, checkpoint-enforced gate that stops Gate G0 sign-off until the
combined corpus reaches the roadmap's 100-document floor.

Purpose: D-04's manifest declarations are worthless without an independent check that a document
actually has the category it claims — and that check must not reuse the future content-stream
interpreter, or it becomes circular. D-02's fork-PR/fresh-clone story only works if absence of the
private tier is silent and green, not a warning or a red build. A private tier that is fetched but
never probed or validated defeats the entire point of D-02's "nothing ships with a private-tier
regression" — the fetch alone only proves the bytes arrived intact, not that they are structurally
sound or correctly labelled. And a corpus that can silently stay at ~25-45 public-only documents
never reaches Gate G0 Success Criterion #1's 100-300 target, so this plan ends with a checkpoint
that forces a human to actually populate the private tier before the phase can be signed off.

Output: `tools/probe_corpus.py`, `tools/fetch_private_corpus.py`, `tools/check_corpus_size.py`,
`corpus/private-manifest.json`, three CI jobs (`corpus-public`, `corpus-private-gate`,
`corpus-size-gate`) in `.github/workflows/corpus.yml`, and a blocking checkpoint on the corpus
reaching 100+ combined documents.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| CI runner ↔ external private bucket | Authenticated fetch of real invoices/contracts using CI-scoped secrets |
| CI/local prober ↔ corpus files (including deliberately malformed/encrypted fixtures) | Structural inspection of untrusted-shaped PDF bytes |
| CI/local harness ↔ private-tier corpus files | Rendering and structural validation of real, previously-uninspected invoices/contracts once fetched |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|------------------|
| T-03-01 | Information Disclosure | `PRIVATE_CORPUS_TOKEN` / bucket credentials | mitigate | Fetch script never prints credential values, only status/skip/error messages; GitHub Actions automatically redacts values referenced via `${{ secrets.* }}` from logs |
| T-03-02 | Tampering | Private-tier bytes accidentally committed to git history | mitigate | `.gitignore` entry for `corpus/private/` plus this task's explicit `git check-ignore` verification; a permanent leak risk if ever bypassed, flagged here for a future pre-commit scan as a nice-to-have, not blocking this phase |
| T-03-03 | Denial of Service | Prober/harness hangs or crashes on a deliberately malformed private-tier corpus file | accept | pikepdf's object-layer access is resilient to malformed content streams since it operates on the xref/object table, not content-stream tokens; the harness's renderer subprocess calls already carry explicit timeouts per Plan 01-04; residual hang risk accepted at Phase 1's small-corpus, CI-only, maintainer-only exposure scale — full process sandboxing is explicitly Phase 4 scope |
| T-03-04 | Repudiation | Gate G0 declared "passed" while the private tier is still empty or under-populated | mitigate | `tools/check_corpus_size.py` (Task 3) is a mechanical, CI-enforced check with no bypass; the checkpoint is `type="checkpoint:human-action"`, `gate="blocking"` — it cannot be silently auto-approved |
| T-03-SC | Tampering (supply chain) | No new PyPI/npm packages introduced (stdlib `urllib.request`, `unittest.mock`, `http.server`, `json` only) | accept | Ponytail ladder followed — stdlib solves the private-tier fetch and size gate without a cloud SDK dependency; no [ASSUMED]/[SUS] package introduced |
</threat_model>
