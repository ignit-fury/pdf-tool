<objective>
Prototype and corpus-validate the byte-offset-to-instruction-index correlation bridge (RESEARCH.md
Assumption A3 / Open Question 1) that every module in 03-06 (`engine/rewrite.py`) depends on:
whether a run's own `operator_byte_offset` values -- already computed by playa's walk, carried on
every `GlyphRecord` -- can be reliably mapped to `pikepdf.parse_content_stream()`'s
byte-offset-free instruction-list indices via ordinal position among text-showing operators
(`Tj`/`TJ`/`'`/`"`). Measured directly against the whole 217-document public corpus, not just
hand-picked documents, because a silent tokenizer disagreement between playa and pikepdf on even
one production document would corrupt an unrelated visual run the moment 03-06 is built on top of
an unverified bridge.

Purpose: this is the phase's one genuinely unproven mechanism -- everything in 03-06/03-07/03-08/
03-09 assumes this bridge holds. Proving or disproving it here, in Wave 1, alone and parallel to
nothing that depends on it, means a failure is caught before four downstream modules are built on
a broken foundation -- the same role Phase 1's TJ-refit spike played for the width-fit math.

Output: `spike/instruction_correlation_probe.py`, `tests/test_instruction_correlation_probe.py`,
`tests/test_instruction_correlation_corpus.py`, `A3-CORRELATION-RESULTS.md`.
</objective>

From `engine/run_id.py` (read in full for this plan):
```
def decode_run_id(run_id: str) -> RunIdParts
def resolve_run_id_offset(run_id: str, original_bytes_by_part: dict[int, bytes]) -> bool
class RunIdParts(TypedDict):  # source_hash, page, part, xobj_path, annot, pattern, charproc,
                               # byte_offset, subrange
```
`o` in a run_id is "the byte offset of the operator keyword token within its own decoded
content-stream *part*" -- confirms `operator_byte_offset` is part-scoped, not page-scoped or
document-scoped: correlating it requires grouping by the same part index, not just the same page.

From RESEARCH.md Pattern 1 (the sketch this plan implements against):
```
def touched_instruction_indices(
    stream_bytes: bytes,
    instructions: list,               # pikepdf.parse_content_stream(...) result, same bytes
    run_operator_offsets: set[int],    # from run.glyphs[i].operator_byte_offset, this run only
    all_operator_offsets_sorted: list[int],  # every distinct operator_byte_offset on this part
) -> list[int]
```
`GlyphRecord.operator_byte_offset` (cited at `engine/records.py` line 31 per 03-PATTERNS.md) is
the field this bridges FROM. `RunRecord.glyphs` is the list of a run's own `GlyphRecord`s (per
RESEARCH.md's own pseudocode comment: `run.glyphs[i].operator_byte_offset`).

From 03-PATTERNS.md (`engine/rewrite.py` section, "No analog" callout): correlating a run's
`operator_byte_offset` to pikepdf's instruction-list index "is new code with no precedent anywhere
in `engine/`... Treat this as a Wave 0 spike task, not something to derive by reading existing
code -- there is nothing to read." This confirms the executor must design the glue (how to fetch
"every distinct operator_byte_offset on this part" across all runs, and how to fetch that part's
own decoded bytes) directly from `engine/index.py`/`engine/records.py`/`engine/classify_run.py`
during read_first, not from an existing analog.

`engine.classify_run._stream_bytes_and_resources` -- the existing private helper
`engine/identity_rewrite.py` already imports to get a page part's own decoded bytes + resources.
CONTEXT.md's Integration Points section: "Flagged in review as acceptable for two consumers; the
rewrite engine [03-06] would be a third, at which point promoting it to a public API is the cheap
fix." Reusing it from this spike is fine and matches "don't reimplement part-splitting logic."
